# Symbo — Documentation-vs-Implementation Audit

**Date:** 2026-09-07
**Scope:** the four documents in `docs/` (Technical Whitepaper, Owner's Manual, Core
Mathematical Methods, Architectural Basis Essay) plus `docs/MILITARY_GRADE_NANOTENSOR.md`,
audited against the code on branch `arena/01a07ad1-symbo` (base `e7eebfd`).
**Method:** every substantive claim in the documents was traced to code, executed, and —
where the claim is mathematical — checked against an *independent* re-derivation written
outside the package (so the engine could not grade its own homework).

**Environment:** Python 3.11.2, sympy 1.14, numpy 2.4.6, networkx 3.6.1. Optional extras
(torch, matplotlib, plotly, msgpack, pyarrow, skopt, kanren, streamlit, dill) not installed.

**Baseline health:** `pytest` → **500 passed, 16 skipped** (all skips are missing optional
extras). `ruff check .` → clean. So this audit is *not* about a broken build; it is about
where the documents promise more, or something different, from what the code does.

## Findings

### F-1 — CRITICAL: the second-order perturbation solver produces coefficients that do not solve the model

This is the flagship claim. Whitepaper §7.1: *"The resulting symbolic Taylor polynomial
accurately reproduced the closed-form coefficient values found in traditional, specialized
macroeconomic solvers."* It does not.

**Root cause** — `symbo/analytics/perturbation.py`, `_variable_substitutions`, line 525:

```python
shifted = policy.subs({d: one_step(d) for d in self.drivers})
```

`policy` is a polynomial in the *deviation* symbols (`Delta_k`, `Delta_a`), but the
substitution dict is keyed by the **driver symbols** (`k`, `a`), which do not occur in
`policy` at all. The substitution is therefore a **no-op**: the expectation of a control one
period ahead, `c_{t+1}`, is silently set equal to `c_t`.

Reproduced directly:

```
c_next -> Delta_a*g_c_a + Delta_k*g_c_k + 1.48293697563485     # identical to c_t
```

The Euler equation consequently degenerates. Its first-order condition on `Delta_k` collapses
to `≈ 0·g_c_k + 0.0044·g_k_k = 0`, which is why the solver reports `g_k_k = 0.0` — capital has
*no* persistence — and the test suite enshrines this as *"no adjustment costs: next-period
capital is not driven by today's level"* (`tests/test_perturbation.py:87`). In the textbook
RBC model capital persistence is ≈ 0.91–0.95; zero is economically impossible (it would mean
the entire capital stock is rebuilt from scratch every period).

**Independent check.** Solving the demo's own model numerically outside Symbo (Newton on the
4 unknown linear coefficients, residual 5.9e-10):

| coefficient | Symbo | independent solve |
|---|---|---|
| `g_k_k` | 0.000000 | **0.942917** |
| `g_k_a` | 12.246729 | **0.776859** |
| `g_c_k` | 0.952436 | **0.009524** |
| `g_c_a` | −11.462058 | **0.007848** |

Evaluating the *actual* Euler + resource equations at `h = 1e-3` off the steady state:

* Symbo's coefficients → max residual **1.71**
* independent coefficients → max residual **4.2e-07**

**Why nothing catches it.** The residual harness `_residual_at` re-uses the same broken
`_variable_substitutions`, so it validates the policy against the same mis-stated model. It
reports `3.4e-10` for coefficients whose true residual is 1.71 — the verification is circular.
Every downstream guarantee inherits this: `diagnostics['residual_h*']`, the
`scaling_exponent ≈ 2 / ≈ 3` "direct evidence that the announced order was achieved"
(docstring, line ~921), the `test_residual_scaling_exponent_matches_theory` test, and the
`risk_corrections` (`h_k_sigma_sigma = 8.61`) built on top of the second-order terms.

**Additional model bug in the demo.** `symbo/demos.py:111` writes the resource constraint as
`alpha*exp(a)*k**alpha + (1-delta)*k - c - kp`, i.e. output is `α·A·kᵅ`, not `A·kᵅ`. The
docstring three lines above (line 71) states the correct `y = exp(a)k^α + (1-δ)k - c`. The
same `alpha *` typo is in `tests/conftest.py:35` and `tests/test_perturbation.py:38,235`, so
the tests validate the typo. It also makes the printed steady state inconsistent: the demo
reports `c = 0.087968` while the true log-utility RBC steady state for these parameters is
`c = 1.4829` (which the module-level solver *does* return when the constraint is written
correctly — see below).

**Note:** naively fixing line 525 to key on `deltas[d]` makes the first-order conditions
genuinely nonlinear in the coefficients (`g_c_k*g_k_k` cross terms appear, as they must —
this is exactly the quadratic matrix equation that real perturbation solvers handle with a
Schur/QZ decomposition or a Sylvester solve). `_solve_linear_system` then raises
`LinAlgError: not linear in the coefficients`. **The fix is not a one-liner**; the first-order
stage needs a proper generalized-eigenvalue (Blanchard–Kahn / Klein / QZ) step, and the
second-order stage a Sylvester solve. Until then the module should not claim to reproduce
reference solver output.

**Recommended actions**
1. Mark `SecondOrderPerturbation` experimental and remove the "reproduces closed-form
   coefficients" claim from the whitepaper and the module docstring until it is true.
2. Replace `_residual_at` with an *independent* evaluator that substitutes numerically into
   the raw user equations, never through `_variable_substitutions`. Add a regression test
   asserting the residual at the known-good RBC coefficients is < 1e-6 and at `g_k_k = 0`
   is > 1. This single change would have caught the bug.
3. Fix the `alpha *` typo in `demos.py`, `conftest.py`, `test_perturbation.py`.
4. Implement the QZ/Sylvester first-order stage, or document the restriction.

### F-2 — HIGH: A* pathfinding is not admissible, so "optimal path" is false

Whitepaper §5.3, Manual §4.3 and Methods §5.3 all state that `f(n) = g(n) + h(n)` with a
Manhattan heuristic finds "the optimal path" / "the most efficient path".

`NanoTensor._heuristic` (`nanotensor.py:787`) returns raw Manhattan *step count*, while
`g` accumulates **grid cell values** (`cost_grid[nb]`), which are arbitrary reals. A
heuristic is admissible only if it never exceeds the true remaining cost; a step-count
heuristic over a value landscape has no such relation. On 50 random 6×6 grids with cell costs
in [0, 2), the returned path was **suboptimal in 24 of 50 cases** versus a Dijkstra reference.

Worse, on *any* landscape with negative values (which `compute_grid` readily produces, and
which `mode='max'` produces by construction via `cost_grid = -Z`) the algorithm is unsound in
principle. The code acknowledges this — there is a comment about a cycle guard added because
re-opening nodes made path reconstruction loop forever — but a closed set does not restore
optimality, it only bounds the search.

The separate `SymbolicAStarPathfinder` in `reasoning/a_star.py` has the same problem by
design: `heuristic()` is `0.5·euclidean + 0.3·|ΔE| + 0.2·weighted_dist` — an arbitrary
weighted blend, with a comment claiming the weights "ensure admissibility". They do not; no
bound relates that expression to `edge_cost`.

**Recommended actions**
- Either scale the heuristic by the minimum cell cost (`h = manhattan · min(Z)`, valid only
  for non-negative `Z`) and reject negative grids, or set `h = 0` and document the routine
  honestly as uniform-cost/Dijkstra search — which *is* optimal and is what the code
  effectively wants to be.
- For negative landscapes use Bellman-Ford/SPFA or shift the grid by its minimum.
- Change "optimal path" to "low-cost path" in all four documents unless (a) is done.

### F-3 — HIGH: `SymbolicTrainer.fit(method='perturbation')` does not use the audited engine

Owner's Manual §5.1 presents `.fit(data, method='perturbation')` as the single entry point
for "a full second-order perturbation analysis", and Blueprint §6.1 walks the reader through
exactly that call. But `fit` routes to `NanoTensor.full_perturbation`
(`nanotensor.py:1562`), a *different* implementation from
`analytics/perturbation.py` — a sequential, single-residual root-finder that picks
coefficients by `min(candidates, key=abs)` ("economically meaningful root"), an unjustified
selection rule.

`HANDOFF.md` §6.5 already flags it: *"`full_perturbation` … remains fragile (that is the
routine that hid the steady-state hang). The user-facing demos no longer use it, and it has
no tests."* The audit confirms both halves:

- Running the Manual's Blueprint 6.1 verbatim on a realistic RBC residual **hung for >10
  minutes** and had to be killed.
- On a trivial residual it "succeeds" while emitting `Failed to solve sigma term: expected a
  one-dimensional and numerical function` to stdout and returning a single coefficient
  (`g_sig_sig`), yet `fit()` returns `True`.

So the most prominent documented workflow points at the least trustworthy code path, and its
success flag is unreliable.

**Recommended actions**
- Re-point `fit(method='perturbation')` at `SecondOrderPerturbation` (after F-1), or emit a
  `DeprecationWarning` and rewrite Manual §5.2/§6.1 around
  `symbo.analytics.perturbation` directly.
- Never return `True` from `fit` on a path that logged a solver failure.
- Replace `print`-style failure reporting with the module logger.

### F-4 — MEDIUM: "finds every possible exact solution" is not what `groebner_solve` does

Manual §4.2: *"this method finds **every** possible exact solution to the system
algebraically"*, and *"returns all valid solutions"*.

Observed (`nanotensor.py:1304`):

| input | returned |
|---|---|
| `x**3 - 1` for `x` | `[{'x': 1}]` — the two complex roots are dropped |
| `x + y - 1` for `x, y` | `[]` — a 1-parameter solution family, silently empty |
| `[x-1, x-2]` (inconsistent) | `[]` — same empty list as the underdetermined case |
| `x**2+y**2-1, x-y` | both real roots ✅ |

Two issues: (a) the real-solution filter is undocumented in the Manual — legitimate for the
stated use cases, but "every possible solution" is wrong; (b) an under-determined system,
an inconsistent system, and an internal failure are all reported as `[]`. The bare
`except Exception → logger.warning → return []` at line 1343 makes silent wrong answers the
default. Note `handle_infinite_solutions` exists in `solver/groebner.py` but
`NanoTensor.groebner_solve` does not call it.

**Recommended actions**
- Reword to "all *real* solutions of a zero-dimensional system".
- Distinguish the three empty cases (raise, or return a status object); route
  positive-dimensional ideals through `handle_infinite_solutions`.

### F-5 — MEDIUM: the Kamke ADE demo returns a parametrization in terms of the unknown

Whitepaper §7.2 says the ADE demonstration *"successfully generated the corresponding
parametric equations"*. `demo_kamke_ade()` prints:

```
Parametrization: (x(t), y(t)) = (yp*(yp + 3)/(2*t + 3), t*yp*(yp + 3)/(2*t + 3))
```

Both "parametric" expressions still contain `yp` — the derivative `y'` that was supposed to
be *eliminated*. This is not a parametrization of the ADE; it is the parametrization of the
*conic in (x, y)* obtained by treating `yp` as a constant. `parametrize_curve` hard-codes
`x, y = sp.symbols('x y')` and a line `y = t·x` through the origin, so it silently ignores the
third variable and assumes the curve is singular at the origin.

To be fair, the routine is correct for what it actually is: on the folium
`x³ + y³ − 3xy` it returns `(3t/(1+t³), 3t²/(1+t³))`, the textbook rational parametrization,
and substitution back gives 0. The *ADE application* is the overclaim. The demo's own
docstring is more honest ("serves primarily as a conceptual example"); the whitepaper is not.

**Recommended actions**
- Rewrite the demo to eliminate `yp` (e.g. set `y' = t`, giving `y = (t² + 3t − 3x)/2`, then
  differentiate to get the true parametric pair), or drop the ADE claim from §7.2.
- Have `parametrize_curve` raise when `implicit_poly` contains free symbols other than
  `x, y, t`, and when the curve is not singular at the origin.

### F-6 — MEDIUM: "browser-side inference through WASM" is a naming convention, not a build

Whitepaper §6.2 ("compiled to WebAssembly", "portable browser-side inference"), Manual §7.0
(a capability table listing "WASM Execution"), the Essay, and the README all present WASM as a
delivered capability. `wasm_bindings.py` contains only Python functions with
JSON-friendly signatures plus a test payload. There is no Pyodide/Emscripten/WASI toolchain,
no `.wasm` artifact, and no build target anywhere in the repo (`build_desktop_binaries.sh`
produces PyInstaller *desktop* executables). `HANDOFF.md` §6.7 states this plainly; the
customer-facing documents do not.

**Recommended action** — say "WASM-*friendly* interfaces (JSON/msgpack-serializable
signatures); no browser bundle is produced by this repository", matching HANDOFF.

### F-7 — MEDIUM: the "10× slower than NumPy" benchmark measures ~500×

Whitepaper §7.3 and Manual §7.0: *"symbolic differentiation within Symbo is approximately ten
times slower than numeric differentiation using a library like NumPy."*

`benchmark_performance()` on this machine:

```
Symbolic diff: 0.1174s   Numeric diff: 0.0002s   Speed ratio: 538.10x
```

Beyond the number, the comparison is not like-for-like: it times
`NanoTensor.diff_cached` on a 100×100 tensor of *default* expressions against
`np.gradient` on random floats — different operations (exact symbolic derivative vs. finite
difference) on different data.

**Recommended actions** — quote a measured range with hardware and expression complexity, or
delete the figure. Note the benchmark is a finite-difference comparison, not autodiff.

### F-8 — LOW: the "318 classical algorithms" provenance is unverifiable

All four documents open on it. In the repo the number appears only as prose in `README.md:9`,
`MODULES.md:32` and the `primitives.py:13` docstring. `AtomicPrimitives` is a compact utility
class; there is no catalogue, bibliography, or mapping from any algorithm to any primitive.
The claim is the rhetorical foundation of the whitepaper's "new model class" argument and is
currently unfalsifiable.

**Recommended action** — ship `docs/algorithm-corpus.md` listing the 318 with their extracted
primitives, or soften to a qualitative statement.

### F-9 — LOW: `MILITARY_GRADE_NANOTENSOR.md` example uses a module that does not exist

Line 33: `from symbo.symbo import NanoTensor` → `ModuleNotFoundError: No module named
'symbo.symbo'`. The correct import is `from symbo import NanoTensor`. The document is not
covered by `tests/test_docs.py`, which only executes blocks in `README.md` and `MODULES.md`.

The document's *substance* checks out: the health thresholds it tabulates (≥0.99 OPTIMAL,
≥0.95 GOOD, ≥0.85 DEGRADED, ≥0.70 CRITICAL) match `nano_tensor_enhanced.py:489-496` and
`nanotensor.py:473-477` exactly, and the 1000-experience buffer matches
`nanotensor.py:301`. But note the doc says "up to 1000 computational experiences" while
`AgencyCore` defaults to `max_memory_size = 10000` — two different buffers, two different
numbers, one document.

**Recommended actions** — fix the import; add `docs/MILITARY_GRADE_NANOTENSOR.md` and
`README_MILITARY_GRADE.md` to the `DOCS` list in `tests/test_docs.py`; reconcile the buffer
sizes.

## What the documents get right

Credit where due — the following were checked and hold:

- The **NanoTensor** is genuinely an n-dimensional container of SymPy expressions with
  differentiation, substitution, caching, lambdify-based numeric evaluation and
  serialization, exactly as Manual §3.0 describes. `.diff()` returns a new tensor without
  mutating the receiver, as documented.
- **`deriv_tree(['k','a'])`** returns the documented `{name: ∂expr}` mapping; verified
  numerically against a linear policy.
- **`stream_groebner_basis`** yields the documented JSON-object chunks.
- **Steady-state computation** is correct: the symbolic solve returns
  `k* = 8.708785` matching the closed form `(αβ/(1−β(1−δ)))^{1/(1−α)}` to 1e-6.
- **`safe_sympify`** is a genuinely careful AST-level guard (pre-evaluation validation,
  explicit `FORBIDDEN_CALLEES` covering `lambdify`/`autowrap`/nested `sympify`, length
  ceiling). This is better than most projects ship and the docs undersell it.
- **Ecosystem integration** (FortArch/Topo/Chrono/Morpho) is presented in both the docs and
  the code as *interfaces with mocks*, and `MockFortArch` is explicitly labelled non-security
  in HANDOFF §6.6. No overclaim.
- **Licensing, authorship and citation** sections match `LICENSE`, `CITATION.cff` (0.2.0) and
  the per-file headers.
- The **layered architecture table** (Tensor Core / Solver / Trainer / Interop / Reasoning)
  maps cleanly onto `tensor.py` + `nanotensor.py` / `solver/` / trainers in `nanotensor.py` /
  `io/` + `wasm_bindings.py` / `reasoning/` + `analytics/explain.py`.
- **`HANDOFF.md` is an honest document.** Several of the findings above are already recorded
  there as known limitations. The gap is that `docs/` — the material an external reader
  actually receives — does not reflect it.

## Priority queue

1. **F-1** — fix or retract the perturbation correctness claim; replace the circular residual
   check first, since it is what allows the error to persist. Blocks any research use.
2. **F-3** — stop routing the documented API at the untested `full_perturbation`.
3. **F-2** — make A* admissible or stop calling its output optimal.
4. **F-5**, **F-4** — correct the ADE and Gröbner completeness claims.
5. **F-6**, **F-7** — align the WASM and benchmark claims with HANDOFF's own wording.
6. **F-9**, **F-10** — extend `test_docs.py` to cover every markdown document, so doc drift
   becomes a test failure rather than an audit finding.
7. **F-8** — publish the algorithm corpus or soften the framing.

A single structural recommendation underlies most of these: **the `docs/` PDFs are marketing
artifacts that were never wired into CI.** `tests/test_docs.py` already proves the pattern
works for `README.md` and `MODULES.md`. Extending it, and treating the whitepaper's numeric
claims (coefficient values, benchmark ratios) as assertions rather than prose, would convert
this class of finding into a build error.
